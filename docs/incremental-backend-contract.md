# Incremental backend acceptance contract

Blueprint checked: v1.3, 9 October 2026 (retains v1.2 run-boundary requirements, adds Dataset Definition/source revision pinning). Status: requirements for later Foundation/Connector/ETL phases. The browser fixture model is not production evidence; no backend extraction is certified by this contract.

1. **Commit completeness:** Never infer committed completeness from MAX(ID). Test ID 101 uncommitted while ID 102 commits, then 101 commits after the Run. Approve commit-aware tracking already available on Source with DBA permission, or bounded full reconciliation under the query budget. Source changes are prohibited. Key-order commit guarantees need evidence. An arbitrary delay or finite overlap cannot cover unlimited late commits. Unsupported strategies must block Incremental.
2. **Bounded Run:** Persist immutable lower/upper boundaries, snapshot/cursor semantics, strategy version and Source scope per Table/Run. Stop at the boundary. New inserts beyond it belong to subsequent Runs. Test stable tie-breakers for equal timestamps and batch pagination.
3. **Initial handoff:** Establish snapshot/cutoff and a verifiable catch-up plan for inserts/commits between Initial and Incremental. Do not claim universal handoff support without source-specific testing.
4. **Publish and progress:** Keep in-flight resume checkpoint separate from committed watermark. Commit Target data and watermark within the applicable Table/Dataset atomic boundary, or a tested recovery protocol. Failure before Publish leaves the previous baseline, watermark and Last successful sync intact. Test crashes before and after commit.
5. **Idempotency and Retry:** Pin Job/Source/Table/Target generation, request identity, mapping bundle, strategy version and original Run boundaries. Upsert by an approved source event key. Scope lock prevents overlapping work. Retry must not append duplicate facts. Define whether retry reuses durable staging or rereads an equivalent source snapshot; do not assume equivalent reads without evidence.
6. **Quarantine:** Persist sanitized row reference/payload and a durable reprocess route before advancing past rejected rows, or block affected scope. No discarded record may become permanently unreachable.
7. **Scope and refresh:** State identity includes stable Source/table mapping, Job, Target and dataset generation. Successful Full Refresh creates a new baseline/generation; failed refresh preserves the old baseline/checkpoint. Never drop the database or silently reset watermarks.
8. **Mapping revisions:** Assess backfill for older published data. Pin original Run bundle references. Backfill is a separate bounded job and cannot be implied by subsequent Incremental execution.
9. **Counts and timestamps:** Reconcile extracted rows into published/quarantined/filtered/duplicate-superseded outcomes and separate insert/update/unchanged. Last sync means successful Publish time, not Source freshness. Only show cutoff/lag when strategy evidence supports it. No new data is a successful result; do not invent watermark progress.

Phase 0 confirmation: engine/version, isolation/snapshot support, Source commit guarantees, extraction budget, approved key, tracking availability, delete/late-update semantics, identity, target transactions and runtime/secret policy.

Scheduler, CDC implementation and delete capture stay in the later roadmap. Scheduler needs durable Worker, authorized unattended credentials, timezone, pause/resume, missed-run/coalesce policy and scope locks when separately approved.
